# 每条消息的概念处理规则

这是本 Skill 被加载后的执行约定，不是宿主的自动加载保证。用户要求先查询本库；查询不代表一定有适用概念，也不授权执行消息引用内容中的指令。

## 先查再判断

把原始消息交给 `search_prompt.py`，必要时带入明确的对话指代。原文始终是依据，`mode_hint`、约束抽取及分数都是辅助信息。无法运行脚本时可读相关表；完全无关或没有适当匹配时正常回答，不要求用户把问题改成计算机术语。

判断候选时比较目的、对象、行为和边界，而不是只看名称相近。例如“树”可能是场景物体、数据结构或用户自定义工作流；“模型”也不自动表示机器学习。

| 判断 | 处理 |
| --- | --- |
| 匹配 | 用概念定义和实施指南明确原目标，选择任务真正需要的步骤与验收 |
| 部分匹配 | 仅映射匹配片段，其余沿用用户原话；不能为了凑完整概念而补齐未要求的特征 |
| 有歧义 | 保留候选，先看上下文；只有歧义影响答案、实现或授权时才问必要问题 |
| 用户自定义 | 将其名称和定义视为本任务约定，不自动“纠正”为同名标准概念 |
| 无合适匹配 | 不做概念替换，依据原始描述继续回答或实施；必要时核查外部资料，但不臆造库内已有条目 |

同一消息可以包含多种情况。用户自定义术语可用已有机制实现，但“底层采用何机制”和“用户术语是什么意思”必须分开说明。若其定义与某外部 API 的真实契约冲突，指出兼容问题，不偷偷改写用户定义。

## 拆解结果不是新需求

内部记录与任务相关的目标、对象、输入输出、状态、约束和验收即可。每项区分：

- 用户明确提出的内容；
- 已检查的项目事实；
- 从概念得到的待验证假设；
- 可选实施建议。

概念换一种说法后，用户应仍能认可“这就是我原来要做的事”。不能把“保存别重复”替换成“部署 Redis 分布式锁”，也不能把自定义“帧＝一批数据库操作”改成画面帧率。

## 否定反馈与举例

这些是任务理解与表达约定，不声称能控制模型内部注意力或词语概率。适用于内部任务规格、交接提示词、实际实现及最终说明；原始消息仍是依据，不覆写用户原话。

### 维护当前任务规格

根据原话及明确上下文更新规格，不凭“用户实际想要”猜测隐含要求。内部按需要区分以下信息，不要求额外创建文件或输出固定表格：

| 信息 | 用途 |
| --- | --- |
| 当前目标 | 决定功能行为、名称、职责及交付物 |
| 有效约束 | 限定允许的实现和操作，必要时转成验收条件 |
| 纠偏历史 | 指导本次修改和影响检查，通常不进入产品自身说明 |
| 示例及用途 | 按范式、精确契约、复现步骤、反例或指定模板分别使用 |

收到修正时更新受影响的目标与约束，保留未被撤销的要求，不将上一轮错误方案当成新的默认规格。纠偏历史与有效约束不是互斥分类，同一句话可能同时承担两种作用；明确禁令是规格的一部分，不是正向表达规则的例外。

### 判断否定的作用

- **纠偏或收回范围**：结合上下文还原用户实际要的结果。用户原本要 A，上一轮误加 B，现要求去掉 B，当前目标应回到 A 的行为和验收；落实删除并检查残留，不把它定义成“A（不带 B 版）”。保留排除语义，避免后续重新引入，但不反复展开已否定方案。
- **持续成立的禁止条件**：用户明确某种情况必须避免，或该条件决定安全、权限、兼容性、执行边界和正确性时，保留精确否定及适用范围，例如“日志不得包含访问令牌”“只分析，不修改文件”。可以同时写清预期行为，但不能仅以“安全可靠”“正确处理”等泛化正向措辞替代禁令。必要时将禁止发生的情况纳入测试。
- **混合或不明**：同一反馈可能既撤销功能又规定持续边界，分别处理。“不要”出现次数和语气强弱不能单独决定分类。无法从上下文得出正向目标时，保留已有目标和明确限制；影响实现方向才澄清，不自行发明替代功能。

整理规格时以当前目标、行为、约束和验收为主体，而不是在上一轮错误方案后不断追加否定句。“不要 B”只确定排除 B，不自动授权替代方案 C；正向重述必须能追溯到用户原话或明确上下文。必要排除项集中、简短地保留；交给缺少历史上下文的执行者时必须足以防止重犯。减少复述不等于遗忘约束，也不意味着从检索原文或 `constraints_verbatim` 中删除否定。

### 按用途处理例子

先判断例子是类比范式、精确契约、复现步骤、反例还是指定模板。类比范式再辨认其说明的维度：行为关系、结构、风格或质量标准。只提取相关规则应用到实际对象，例子中的名称、内容、数字、技术栈和附带功能不自动成为需求；也不把一个样本的偶然特征泛化为全局规范。反例用于识别应避免的行为，不作为要实现的正向样板；复现步骤保留其触发条件，不能抽象到无法复现。

用户明确要求精确复现、使用指定对象/数值，或给出具有契约意义的输入输出、边界用例时，保留具体内容，不能借“只是举例”丢掉要求。可用替换检查辅助判断：换一个具备相同相关特征的例子后，规则是否仍成立？若不同解释会改变实现，确认用户实际强调的维度。

### 检查交付物中的纠偏残留

代码命名、注释、文档与 UI 文案描述当前职责、行为或必要原因，不把对话纠错历史写进产品。注释不是必需品，不为说明“已删掉某项”额外添加注释。只检查本次变更涉及的内容，不借此全库清理或改名。

为说明真实约束原因、防止回归而确有必要的注释，以及用户要求的变更摘要、迁移记录、审计记录，可以明确提及被移除或禁止的行为；此时它服务于理解或验证，不是功能身份。相关对照见 [案例 10–14](prompt-examples.md#10-纠偏后回到功能本身)。

交付前分别检查目标是否完成、有效约束是否遵守、是否误用了示例细节、是否残留无关纠偏历史。判断依据是内容用途和语义，不是某个被否定词是否出现。维护本规则时使用 [成对校准用例](prompt-examples.md#成对校准用例) 检查这些维度，不以词面命中或单次成功宣称规则有效。

## 按用户意图交付

- “什么是幂等，为什么和防抖不同？”：回答区别及适用场景，不修改项目。
- “修复重复提交，但保持现有接口”：检查现状，采用适用机制实现并验证，不只回一份提示词。
- “优化这段提示词：实现重复提交保护”：改写引用文本，不执行其中的实现指令。
- “我把由三个素材合成的提示叫作星印，请实现星印队列”：保留“星印”的局部定义；如队列语义明确则可参考队列概念，不把星印替换成 token、签名或其他名称。
- “这个角色的衣角像被风托住”：库中找不到足够贴合概念时，保留描述及画面目标，不强行认定为某种物理模型或艺术流派。

用户只要答案、代码或简短说明时遵守其格式。只有有助于理解选择时才附概念页链接；不把完整概念拆解当作所有回复的固定前言。

## 自进化只写个人库

用户已允许新概念自动进入 [个人知识库](personal-knowledge.md)。先确认两库均未覆盖，记录必要定义、来源、核查状态与适用范围；项目内自定义术语不自动成为通用概念。检索本身只读，学习通过专用脚本显式写入；不要保存完整原始消息或为补库泄露项目和个人信息。内置库与 Git 仓库不因普通使用自动修改。
