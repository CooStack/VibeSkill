# 音效设计工作流：从听觉目标到游戏验收

独立检索关键词：音效设计、游戏音频、需求简报、分层、包络、频谱、混音、交互、触发、验收、AU001、AU042。

本文件是工作流建议，不是引擎安装教程或统一制作标准。概念及一手资料核查记录见 [audio.md](audio.md#来源与核查范围)，机器可读操作配方见 [audio-recipes.json](audio-recipes.json)。即使不加载主索引，也可按 AU 编号联合查阅。先沿用项目现有音频系统；只有已确认缺口才能提出新增工具或实时 DSP。

## 1. 把形容词变成可判断的目标

对应 AU001、AU002、AU003、AU038。

保留用户原话，例如“重击更厚重，但不能盖过敌人的攻击提示”。分别记录：

- 用户要求：玩家应感知的动作、材质、体量、情绪，以及明确不想改变的内容。
- 工程事实：引擎/中间件及版本、目标设备、视角、事件来源、现有总线、资源格式和预算；没有查看的标为未知。
- 设计假设：例如“主体缺乏共振，而不是整体不够响”；用试听证明，不能直接升级为需求。
- 可选方案：增加材质层、改变衰减、减少背景密度等，先做最小对比再决定。

为参考片段标出具体时刻和用途：是起音、主体、尾声，还是整体风格？同时记录不应复制的部分及素材来源。选一个“现有可接受声音”作锚点，在相同监听设置下比较；不要只靠不同网站播放器的音量判断。

产物：一段可独立理解的声音简报，说明“谁在什么情境做什么，玩家应听懂什么，哪些条件必须保持，怎样判定改进”。

## 2. 先定义信息，再决定素材数量

对应 AU004、AU005、AU006、AU009、AU031、AU039。

把动作画成声音时间线：准备、接触、结果、余韵。不是所有动作都要四段；瞬时反馈可能只需一个清晰起音。逐段写出“这一段告诉玩家什么”。

制作一版最小可用声音后，再检查缺口：

- 起音缺少接触感：先检查同步和攻击段，不先堆低频。
- 主体缺乏材质：更换有合适共振/摩擦细节的素材，或只补对应层。
- 尺度不足：试听主体时长、音高运动和衰减关系，不预设“越低越大”。
- 空间不成立：区分声音本体尾声与游戏房间混响，避免重复烘焙。

每加入一层就做静音对比；删掉后没有损失的层通常不值得保留。记录必须固定的识别层和允许随机的装饰层。只有需要独立参数、空间位置或动态混音的层才优先留到运行时；固定关系可以离线合成，减少资源开销。

产物：可试听草案、各层职责、保留/删除理由，以及干声母版。录制时保留原始 take，不在唯一母版上做破坏性清理。

## 3. 修形态，而不只是修音量

对应 AU007 至 AU016。

先对齐感知起音，再调整包络；在游戏实际重复速度下试听衰减与尾声。持续音要分别设计正常释放与取消释放，不能只检查完整播放。

频谱处理前先检查是否有两层在同一时刻表达同一件事。优先删层、缩短尾声或改变编排，再在上下文中调整 EQ。找刺耳点时可短暂诊断性扫频，但最终回到正常监听音量判断，不把扫描时的峰值当作必削规则。

动态处理一次只检验一个目的：控制异常峰值、让力度更稳定，或添加质感。旁路比较时调整监听增益，避免将更响误认成更好。检查单声道求和，尤其是宽化或相关低频层。

数字峰值、真峰值和节目响度是不同观察量。先确认项目和交付渠道要求，再选仪表、窗口和限值；不为所有短音效指定同一 LUFS，不将数字电平换算成未经校准的听力安全结论。

产物：干/湿版本、可回退处理链、已确认的测量方法。缺少交付规范时记录“待确认”，不用网络常见数值补空。

## 4. 为交互写一份小契约

对应 AU024 至 AU030、AU040、AU041。

每个事件至少写清以下字段；这是交付信息，不要求改成新的代码框架：

| 字段 | 需要回答的问题 |
| --- | --- |
| 语义与触发 | 按下、实际接触还是权威命中？哪个系统唯一负责触发？ |
| 事件身份 | 谁发声、哪次动作、如何辨别预测与确认是否同一次？ |
| 空间 | 跟随哪个对象/骨骼？在哪里停止跟随？谁是 listener？ |
| 参数 | 材质、力度、速度等的单位、值域、缺省、作用域是什么？ |
| 生命周期 | 瞬发还是持续？重入、取消、暂停、死亡、卸载分别怎么办？ |
| 并发 | 按角色还是类别限额？达到上限是拒绝、替换还是虚拟化？ |
| 资源 | 何时加载、怎样确认就绪、谁持有并在何时释放？ |
| 降级 | 资源缺失或预算不足时保留什么关键信息？ |
| 可观测性 | 怎样记录触发、拒绝原因、当前状态和实例归属？ |

素材就绪后尽早接进实际场景，不等所有变体制作完才检查触发。给循环实例分配明确所有者；持续更新参数，不在每帧创建声音。联机场景分别测试预测成功、被否决、延迟确认和重复消息。

产物：事件契约、状态转移表与少量可重放的场景。引擎 API 名称、线程和销毁语义必须以项目版本核对，本指南不作跨引擎承诺。

## 5. 在实际混音与空间里做取舍

对应 AU003、AU017 至 AU023、AU027、AU037、AU039。

至少保留安静探索、正常交互、密集战斗和关键警告同时发生的试听场景。先听主角动作和警告能否辨认，再逐步加入环境、远端事件和音乐。为背景安排让位，不将所有资产逐个推响。

距离、方向、遮挡、混响分别开启比较，确认每项解决的问题。走过门洞、绕墙、转镜头、贴近声源、进入远距边界；录下突变点，检查曲线、单位、listener 和状态更新。

用户音量设置与临时混音状态应分别保存。检查不同类别的滑杆、静音、单声道及关键视觉/字幕提示；核心信息不能只剩被用户关闭的声道或触觉。

产物：场景混音基线、空间测试轨迹、类别优先级和允许删减的装饰内容。

## 6. 导出和资源策略需要回到真机验证

对应 AU033 至 AU036。

保留源工程与无损母版；交付清单写明事件语义、版本、变体分组、声道、循环区域、尾声、来源及权利状态。按已核实的项目规范导出，不自行改变整个项目采样率或编码体系。

针对首播关键短音、密集重复短音、长环境、音乐/对白分别评估加载策略。记录打包后大小、解码后内存、首次触发、流式读取与音频线程开销，不把压缩文件大小当作运行内存。

重新导入实际构建并试听：检查自动归一化、重采样、编码延迟、首尾裁切、循环点及声道变化。bank 或资源清单更新后，验证媒体确已打入包并加载，而不是只在编辑器缓存中可用。

产物：资产清单、平台转换后的试听记录及负载记录；未测的平台必须标注未测。

## 7. 验收与回归

对应 AU038、AU042。阈值由用户目标、项目预算与真实基线决定；以下是观察方法，不是统一通过数值。

| 维度 | 测试方式 | 应保留的证据 |
| --- | --- | --- |
| 意图与辨识 | 隐去标签比较轻/重、命中/格挡、成功/取消；加入实际背景再辨认 | 误认类型、参与者反馈与调整理由 |
| 同步与延迟 | 同步录制输入/事件时间与实际播放，区分文件前导及设备输出 | 捕获方法、设备链路、延迟分布及异常 |
| 变体与疲劳 | 按真实最高操作密度连续运行，听重复、尖锐累积、尾声堆叠 | 可重放轨迹、变体选择、失效时刻 |
| 混音与电平 | 重放最密集叠加及关键警告，记录输出仪表和可懂度 | 仪表模式、窗口、混音设置、相对基线 |
| 空间与声道 | 固定移动路线，分别试听耳机、扬声器、单声道 | listener 配置、路线、声道和突变位置 |
| 生命周期 | 重入、取消、暂停恢复、死亡、卸载、重连 | 实例创建/结束/释放记录，无遗留循环 |
| 资源与性能 | 冷启动、首播、峰值并发、低端目标设备长时间运行 | 音频线程/解码/流式负载、内存及声部趋势 |
| 可访问性 | 静音、类别静音、单声道及可用替代提示测试 | 玩家能否获得同一决策信息，缺失项列表 |

交付时区分“设计完成”“资产已制作”“已接入”“已在某设备验收”。只有文档时，只能报告设计和规格核查完成，不得报告已听起来更好、已无削波或已满足性能预算。

## 小型示例：让蓄力重击更厚重

这是可选设计示例，不追加用户未要求的系统。

1. 保留原目标“更厚重且警告可辨”。先录下轻击、重击与警告同现片段，判断缺口是主体、节奏还是混音。
2. 若主因是主体过短，先调整接触后的材质衰减；仍缺质感才增加一个主体层。保持命中识别层稳定，装饰碎屑可做受限变体。
3. 蓄力用持续参数更新；满蓄力提示只在进入满蓄状态时发出。提前取消不播放命中确认；实际命中由结果事件负责。
4. 在密集连续重击中比较两个版本：是否仍能听懂警告、是否越叠越糊、松手和取消是否都结束循环。若不合格，先减少尾声或装饰密度，再考虑动态处理。
5. 记录所改资产、事件参数、试听场景与未测设备；不要把“新增层”本身当作验收成功。
