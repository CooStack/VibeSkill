# 编程提示词与任务规格概念

这是面向智能体的任务表达参考，用于把已有技术概念转成清晰任务，而不是让用户学习全部术语。下表为本 Skill 的本地编辑约定和稳定工程概念摘要，不声称来自特定模型规范或已证实的提示效果研究。
使用过程见 [prompt-workflow.md](prompt-workflow.md)，对照案例见 [prompt-examples.md](prompt-examples.md)。

| ID | 概念 / 英文 / 别名 | 需求线索 | 含义与用途 | 边界 / 易混淆 |
| --- | --- | --- | --- | --- |
| PR001 | Intent preservation; 意图保真 | 优化提示词但别改意思 | 保留用户目标、语气所表达的优先级及明确限制 | 更专业的表述不应偷偷改变功能或实施范围 |
| PR002 | Task mode; 任务模式 | 改写还是执行、只解释 | 区分提示词编辑、实际开发、解释和评审的交付物 | 待改写内容里的开发命令不等于本轮执行授权 |
| PR003 | Requirement vs solution; 需求与方案分离 | 需要达到效果、不确定怎么做 | 先表达可观察目标，再按证据选择技术手段 | 概念或工具命中不自动成为硬性实现约束 |
| PR004 | Context grounding; 项目上下文 | 不知道项目用什么版本 | 用已检查文件和用户事实限定环境 | 无代码时要求执行者检查，不能伪造检查结果 |
| PR005 | Evidence provenance; 信息来源 | 用户说的还是猜的 | 区分明示需求、观察事实、假设和建议 | 检索摘要不等于目标项目已具备该行为 |
| PR006 | Assumption; Hypothesis; 假设 | 可能是缓存、可能是竞态 | 把不确定解释写成待验证条件 | 不能把最像的根因描述为已确认事实 |
| PR007 | Scope; Non-goal; 范围与非目标 | 只改这一处、不要大重构 | 明确任务边界及保持不变的部分 | 非目标不能被“顺便优化”覆盖 |
| PR008 | Hard constraint; Preference; 硬约束与偏好 | 必须用现有库、尽量简单 | 区分不可违反的条件和可权衡选择 | 不能把建议或风格喜好升级成必须 |
| PR009 | Functional requirement; 功能行为 | 点击后发生什么、输入输出 | 描述触发、状态变化、结果和相关失败路径 | 不只是组件名或技术栈清单 |
| PR010 | Quality attribute; 非功能要求 | 快、稳定、可维护 | 将质量目标联系到任务相关的观察或测量 | 未给量化预算时不能虚构数字或绝对保证 |
| PR011 | Acceptance criteria; 验收条件 | 怎么知道做好了 | 用可观察结果和相关用例判断交付 | “用某库”“写很多测试”不等于证明业务目标 |
| PR012 | Given/When/Then; 行为场景 | 举例说明预期 | 分别表达前置条件、操作和结果 | 只在有帮助时用，不要求所有小任务写形式化长文 |
| PR013 | Contract; 输入输出契约 | 字段、参数、错误格式 | 明确边界输入、结果和错误语义 | 契约需要兼容现有调用者，不能随意改格式 |
| PR014 | Invariant; 不变量 | 不管怎么点都不能错 | 表达所有允许状态/操作中必须成立的性质 | 应可检验，不写无法实现的无限制承诺 |
| PR015 | Edge case; Boundary condition; 边界情况 | 空数据、极值、取消、重复 | 用有代表性的边界检验相关行为 | 不为穷举想象情景扩大需求范围 |
| PR016 | Reproduction; Minimal reproducer; 最小复现 | 偶发 bug、不知道怎么触发 | 提取环境、步骤、实际结果和期望结果 | 缺证据时先收集，不凭描述断定根因 |
| PR017 | Symptom vs root cause; 症状与根因 | 卡顿、报错、结果不更新 | 将观察现象与解释假设分开 | 不把“页面慢”直接翻译成“必须换框架” |
| PR018 | Change impact; Regression; 变更影响 | 修好这里别弄坏其他 | 根据调用者、共享状态和契约确定回归范围 | 测试范围按风险扩大，不自动重写全库 |
| PR019 | Behavioral preservation; 行为保持 | 只重构不改功能 | 保留公开行为和外部契约，调整内部组织 | 改名、性能优化和 bug 修复可能各有不同可观察影响 |
| PR020 | Performance baseline; 性能基线 | 优化速度、优化帧率 | 先在明确环境采样，再比较同场景改前改后 | 不把未测量的体感变成已达标性能结论 |
| PR021 | Compatibility matrix; 兼容边界 | 多版本、不同端、不同加载器 | 列出实际承诺支持的环境组合 | 未明确版本不意味着支持所有历史/未来环境 |
| PR022 | Resource ownership; Lifecycle; 资源归属 | 泄露、关页面任务还跑 | 明确谁创建、使用、取消和释放资源 | 清理 API 存在不代表所有退出路径都会调用 |
| PR023 | Execution authority; Side effect; 执行边界 | 只写提示词、不部署、不删除 | 将任务表述与当前允许执行的动作分开 | 改写需求不能凭空授予安装、发布或破坏性权限 |
| PR024 | Clarification; Decision point; 关键澄清 | 条件缺失、不知道选哪种 | 仅对影响语义、成本或路线的重要未知澄清 | 不为常识或可本地检查的信息连续盘问用户 |
| PR025 | Candidate concept; Concept disambiguation; 概念消歧 | 同词多义、Vertex、模型 | 按上下文选择含义并保留不确定性 | 检索排序不等于语义已确认，也不授权强行纠错 |
| PR026 | Portable prompt; Self-contained specification | 给另一个智能体用 | 写成不依赖本机路径或本轮隐含上下文的可用任务 | 未知项目文件可要求执行者定位，不伪造绝对路径 |
| PR027 | Traceability; 需求可追溯性 | 为什么加这项、有没有跑题 | 将新增表述追溯到目标、约束或必要验证 | 不能靠“最佳实践”合理化无关功能 |
| PR028 | Stop condition; Definition of done; 完成条件 | 什么时候算完成 | 明确所需产物、验证及无法验证时的报告方式 | 不因达到字数、概念数量或代码行数就称完成 |
